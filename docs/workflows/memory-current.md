# 当前内存结果

[方法与范围](memory.md) · [loop 内存分析](../loop-workflow.md#统一收尾)

开发提交 `4e2f5f845b8e882d45ba8cd550daf6b99c7611b5` 的 Memory Benchmark `43117120153` 为 release/light，2/2 成功。与 0.7.0 提交 `1af3ca9`、运行 `42978712845` 对比；输入均为 100 节点、5 组、1,000 条规则，工具链、采样时长及内核/Geo 字节一致，runner 实例不同。以下为客户端 RSS 观测峰值，不能推广为全部平台或负载的性能保证。

| 场景 | 0.7.0（MiB） | 当前开发版（MiB） |
| --- | ---: | ---: |
| 首页 | 53.34 | 52.71 |
| 代理组折叠 | 53.58 | 53.11 |
| 节点搜索 | 64.21 | 63.76 |
| 搜索后返回首页 | 56.49 | 55.94 |
| 首页、托盘可用 | 53.99 | 54.08 |
| 关闭窗口、驻留托盘 | 21.99 | 22.13 |
| 20 次窗口重建后 | 59.15 | 59.27 |
| 纯 CLI 后台 | 14.77 | 14.93 |

差异较小且有升有降，不宣称全面改善。普通规则及快捷规则全开两组各完成 20 次销毁/重建，均确认界面进程退出、内核保持运行及纯 CLI 无图形会话。

映射采样修复 ticks/Unix 秒身份比较后，24 个场景共 240 次采样均有效，没有缺失。渲染器匿名加堆私有页的同时间峰值：首页约 3.09 MiB，搜索约 13.33 MiB，返回首页约 5.50 MiB；宿主相应约 3.45、3.81、3.81 MiB。它们是映射采样，不是 RSS 或分配器精确峰值，也不与不同时间的进程峰值相加。

后续优先评估只为视口内节点创建控件：现有 light 搜索最多同时创建 240 张卡片，离页后已释放大部分，但仍存在明确的渲染器增量。实现必须保留原输入、分页、详情、滚动和动效语义，并复测；本轮没有通过减少节点、缩小输入或隐藏进程降低指标。没有新证据时不为微小单轮差值继续改动分配器或全局缓存。

本次仅 Linux x64 隔离环境；Android、Windows、macOS、真实网络业务与长期驻留内存未在此基准验收。
