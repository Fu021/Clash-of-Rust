## 计入与排除

- 覆盖现有六个桌面目标、三个 Android ABI，以及内存基准支持的两种 profile。Ubuntu 20.04 兼容验证复用 Linux 候选包，不虚增另一套编译目标；Android 截图工作流复用 APK，不重新编译。
- 日志确认当前 `CARGO_INCREMENTAL=0`，合计不包含增量目录。若未来明确启用并保存，另预留约 5～10 GiB，再以实测修正。
- 官方分发包、SDK／NDK／JDK 安装目录、预装 VM 镜像、安装包、截图和日志不属于本表。预装 VM 仍只存私网，不能放进 GitHub Cache。
- iOS 仍为宿主占位，未建立正式构建工作流，不把不存在的 iOS 编译缓存计入。将来启用后应单独测量并扩充预算。

估算依据为提交 `5a21964` 的工作流、CI `42712647995` 日志与缓存清单；这是存储规划，不是冷／热编译性能对照。是否值得新增 Go、Gradle 或更多项目对象缓存，应再比较恢复、保存与重编耗时。

## 当前上限与保留预算

维护者最新授权为每月 **1 美元**；2026-11-10 仓库 `max_cache_size_gb` 从 15 调整为 **24 GB**，设置 API 已读回确认。GitHub 此处的 GB 按 2³⁰ 字节计算，即 GiB。10 GiB 免费，超出部分每 GiB 月 0.07 美元；本仓库满额整月约 0.98 美元，账户其他仓库和已产生费用须一并计入预算。账户预算不自动提高仓库上限，两个设置均需配置，见 [GitHub 仓库缓存设置](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository)及[缓存计费](https://docs.github.com/en/billing/concepts/product-billing/github-actions)。

缓存按每小时占用峰值累计，不按配置上限包月。以 30 天、720 小时计算，费用为 `Σ max(每小时峰值 GiB − 10, 0) × 0.07 ÷ 720`。24 GiB 只出现一个计费小时约 0.00136 美元；每天一个小时、其余时间不超过 10 GiB，整月约 0.041 美元。若常驻 10.91 GiB、每天一个小时升到 24 GiB，约 0.102 美元。短于一小时也按该小时峰值计，跨两个计费小时可能同时计入；这些是假设估算，实际以账单为准。

北京时间 2026-11-13 15:18 的逐项清单为 **16 条、19.57 GiB**，全部属于 main，每个逻辑目标各一代：六桌面 Rust 约 12.62 GiB、三 Android Rust 约 5.52 GiB、三 Android Go 约 0.65 GiB、两编译容器约 0.71 GiB、两 macOS Tailscale 约 65.9 MiB；当时没有 Memory profile 或 Gradle 转换缓存。CI `43381550885` 收尾逐项总量同为 19.57 GiB，未发现可按现行代际规则删除的条目。此前 2026-11-10 的 11 条／10.09 GiB 只包含九个平台 Rust 与两份 Tailscale，覆盖和编译设置不同，不能作为当前全覆盖容量目标。

上述 19.57 GiB 是启用 ThinLTO 后的历史快照；当时未逐文件量化中间数据和旧指纹，不能把全部增长归为必需数据。当前[安装包压缩](install-validation.md#安装包压缩)关闭 ThinLTO，升级 Rust 后按维护者授权清空 GitHub Cache 并冷填充；私网原包及两种预装 VM 不删除。新容量和恢复／保存净耗时以本次 Actions 实测更新，不用历史暖编译推断收益，也不因已有 24 GiB 上限填满预算。

CI 与 Memory 共用 `scripts/workflow_storage.py` 的 **20 GiB** 工作预算，低于仓库 **24 GB** 配置上限；余量不保证容纳任何完整归档。main 每个目标和用途只留最新一代，其他 ref 不保留缓存；main 最新代本身超预算时只警告，不删除唯一基线。识别与回收规则统一见[缓存分工](cache-coverage.md#编译对象只用-github)。GitHub 仍可按自身到期或容量规则淘汰缓存，保护和预算均非永久保证；费用以 GitHub 实际账单为准。

本轮新增 Android Go 编译缓存和 Linux 编译环境缓存，继续保留 macOS Tailscale；未新增 Gradle 转换缓存。上表保留全平台容量规划，新增 Docker 编译容器需另按实际归档计量，不能把估算总量写成已经覆盖。Ubuntu 20.04 两种预装 VM 继续仅存私网，不占此额度。首次填充与暖恢复的实际结果分别见下文。

## 近期 CI 耗时依据

2026-11-10 核对六轮完整成功 CI：`42712647995`、`42705403797`、`42697699786`、`42690416513`、`42679544543`、`42655456299`；排除只刷新依赖的运行。各平台恢复与编译的中位数及保留顺序见[缓存分工](cache-coverage.md#编译对象只用-github)。

恢复包含兼容 workspace，桌面编译包含检查与测试，Android 编译包含应用、Go 内核和 Rust，不是纯 Rust 耗时。排队、安装验证、模拟器及清单收尾不用于排序，也不将中位数当作缓存净节约。macOS Intel 整个 job 中位数约 16.6 分钟，其中恢复约 2.3 分钟、编译约 8 分钟；Ubuntu 20.04 ARM64 约 15.8 分钟，包含 TCG 启动、候选包等待及安装验证。它们是主要耗时项，但 VM 继续走私网预装模板，不能因耗时较长就加入 GitHub Cache。

Tailscale 同样影响 CI：macOS ARM64 的 `42679544543` 日志记录从源码安装，接入步骤 166 秒；`42712647995` 两架构命中 31,794,999／34,199,007 字节缓存，接入步骤分别为 3／7 秒。六轮接入中位数为 5.5／7 秒；热态数字短恰好说明小工具缓存有效，不能反过来作为淘汰依据。这不是同一提交的严格冷暖实验，但足以保留约 63 MiB 的两架构工具，避免重复编译。上游源码构建行为见 [Tailscale Action 问题](https://github.com/tailscale/github-action/issues/287)。

## main 基线与分支只读

CI 和 Memory 的开发分支只恢复可信 main 的兼容 Rust 基线，随后由 Cargo 正常重编变化部分；不保存分支对象、差异包或工具副本。Go 对象及 Linux 编译容器同样只由 main 保存。缺少兼容基线时正常冷编译，不绕过 GitHub 的分支作用域。

先前设计的分支差异需要恢复后扫描全部对象建立基线、构建后再次扫描，并校验及叠加归档；实际收益尚未由 Actions 验证。为减少维护和每轮处理成本，现已移除两个 composite action、差异脚本及对应入口。后续只有出现可重复的净耗时收益证据才重新评估。两种预装 VM 继续仅存私网。
