# Ubuntu 20.04 预装测试环境镜像

[返回 CI](ci.md) · [发布核验](release.md) · [服务端对接约定](prepared-vm-protocol.md) · [元数据与向量](prepared-vm-metadata.md) · [现行私网协议](cache-server.md)

2026-11-08 维护者授权复用私网预装模板，客户端覆盖 Ubuntu 20.04 ARM64 和 x64。两种架构分别冻结环境、制作模板和验证恢复，只有服务端显式声明支持的架构才会启用。Actions 已完成双架构真实模板上传、独立暖恢复及安装后验证，证据与测速边界见下文；不改变既有发布。

## 范围与身份

只保存通用测试环境：官方 Ubuntu 20.04 云镜像、5.4 GA 内核、固定 Python 和现有 GUI/授权/网络测试工具。不保存 cor 安装包、Rust 对象、用户配置、运行中内存、旧测试结果或当前 runner 状态。镜像中不能留有构建凭据、私网配置、SSH 私钥或其他运行的访问授权。

环境身份包含架构、官方基础镜像 SHA256、Python SHA256、独立的环境依赖锁和准备配方摘要。环境锁需要补入 CI 冻结输入，包含测试环境包及其解析依据，不能在命中后再去 APT 选择其他版本。发布清单记录实际包名/版本、内核版本、镜像长度与 SHA256，并与冻结清单核对。

环境键只取这些 VM 输入，不含 cor 版本、应用提交、Rust 依赖或整份依赖快照的摘要。准备逻辑应有独立配方，不能直接哈希包含所有测试的整份 Python 脚本；修改窗口测试断言不应重做镜像。改变基础镜像、环境锁、Python 或准备配方才产生新环境键，不使用文件名前缀近似恢复。

CI 的共享输入阶段显式开启 `COR_PREPARED_VM_INPUTS=true`，分别在临时 APT 状态目录解析 ARM64 和 x64 依赖，使用官方签名索引、空安装状态和独立配置，不改宿主 APT，也不依赖私网在线或已声明镜像能力。冻结测试工具的完整解析闭包、版本、原包及 APT 索引；索引随依赖附件传递并复核摘要，锁本身不含 InRelease 刷新时间。仅索引刷新而所选原包未变时可复用同键。独立 Ubuntu Compatibility 再检查能力，未就绪时冷准备；服务端之后上线能力可复用同一提交、同源 CI 的冻结快照重跑兼容验证，不为能力变更刷新依赖。

`scripts/prepared_vm_environment.py` 负责独立准备配方；环境键包含该文件内容与工具清单，不哈希 `linux_ci.py` 的应用测试逻辑。CI 的 `prepared_vms` 按 `arm64`、`x64` 保存独立清单，APT 索引放在 `vm-environment/<架构>/apt`，不能交叉复用。宿主应用快照、guest 冻结安装和安装前环境复核共用 `frozen_environments()`，再以 guest 本机架构选择；只含旧 `prepared_vm` 的快照仅兼容 ARM64，不能用作 x64 环境。ARM64 使用 Ubuntu ports；x64 的基础及 updates 使用 Ubuntu archive，security 使用 Ubuntu security，分别锁定 `arm64` / `amd64` 与 `all` 包。冷路径按冻结版本安装，暖路径比较完整实际包清单和冻结的必需版本；基础盘已有包由官方基础镜像摘要固定。仅下载、不预装应用专有依赖，继续验证安装包声明。

镜像必须正常关机后封装，成为无外部 backing file 的独立系统盘；不保存内存或运行态快照。恢复后重新注入本轮 SSH 授权和实例身份，以只读基础盘加一次性 qcow2 写入层运行；不把测试后的磁盘覆盖回基础镜像。

首版使用 QEMU 自带压缩的 qcow2，不再包一层 tar/gzip。模板封装后检查 qcow2 结构、独立性和实际虚拟容量，并比较转换前后的逻辑磁盘内容。客户端必须先校验文件摘要，再交给 QEMU，不接收带外部数据文件、backing chain、加密或内部快照的模板。

## 客户端路径

1. 尽早按精确环境身份查询私网已提交的镜像，核对清单、大小和摘要后再启动。
2. 检查实际发行版、架构、5.4 内核和环境清单，安装本轮同提交的 cor 包并运行现有全部安装后验证；不复用历史测试结论。
3. 未命中、协议不可用、身份或内容校验失败时，退回现行官方镜像与 DEB 准备流程，保留明确的未命中或错误原因。
4. 现行流程准备好通用环境后，才生成可复用镜像。生成和上传耗时单列，不把首次构建的额外开销隐藏在测试中。

模板准备、恢复与安装验证由独立 [Ubuntu Compatibility](ubuntu-compatibility.md) 双架构 job 执行，Publish Release 核对其成功回执，不重启 VM。预装镜像只存私网，禁止写入 GitHub Actions Cache，包括压缩镜像、基础盘和写入层；不以 artifact 或公开 Release 中转镜像。runner 只用本轮临时文件，GitHub 附件只保存小型清单、摘要、回执和耗时，Rust 缓存预算不变。

接入时将镜像工作目录放在 runner 临时目录，与 Rust 缓存、安装包和报告目录分开；证据上传按文件白名单收集，不上传镜像工作目录或其父目录。即使私网不可用，也只能回退冷准备，不能转存 GitHub。这项限制覆盖三条工作流的缓存保存、附件上传和最终发布入口，不能只靠镜像扩展名过滤。

## 模板的生成与恢复

首次未命中仍在可丢弃 Actions 环境完成现有准备。依赖安装完成后、安装 cor 之前制作模板；清除构建源目录、测试报告、本轮授权、cloud-init 实例状态、主机密钥和机器身份，关闭机器后离线封装。清理仅限该临时 guest，不操作 runner、当前开发服务器或私网服务数据。按 guest 实际 cloud-init 版本检查可用选项，不能照抄新版本命令。

模板在第二次独立启动中证明可重新注入新身份和 SSH 授权，并核对完整包清单。此后用模板的临时写入层继续本轮 cor 安装和测试，不能跳过冷路径的应用验证。环境刷新时重新做该冷准备和模板恢复验收。

SSH 就绪探测的单次 15 秒超时只是尚未就绪，会在原有 600 秒总预算内重试；QEMU 退出或总预算耗尽仍立即失败。`cloud-init` 完成、5.4 内核、完整包清单及应用验证仍分别检查，不以 SSH 端口出现代替启动成功。

模板在清理源目录、旧 SSH 授权、主机密钥、机器身份和日志后，对支持 discard 的临时系统盘执行根文件系统 TRIM，再正常关机、压缩转换并比较逻辑磁盘内容；清理或 TRIM 失败时不上传候选。默认 zlib、独立 qcow2，先做有界头部检查，再做 QEMU 完整检查。关闭的 APT 自动更新任务也属于该一次性环境配方，避免冻结后自行变更依赖，不操作开发服务器。

暖路径只恢复模板、启动新实例、校验环境及安装 cor，不再无条件执行 `apt update` 和整套 GUI 工具安装。环境不符或安装仍需额外环境工具时明确记录未命中并冷准备，不能静默补装后宣称完全暖命中。安装 cor 自身声明的依赖属于应用安装步骤，继续如实记录。

已提交镜像无法启动或清单不符时，本轮改走完整冷准备，不尝试用新镜像覆盖相同的不可变环境键。暖恢复还会核对冻结原包的摘要及大小覆盖；冷回退不能掩盖之后的应用安装或测试失败。

## 服务端与工作流分工

首版使用专用认证流式上传，服务端保存模板和元数据，并验证 qcow2 头部及外部依赖，不在服务器制作镜像或启动 QEMU。不恢复通用 PUT，也不将模板写进 `upstream/files`。维护者报告服务端已部署五个接口及不可变环境键；接口、额度、认证、生命周期及回执以[对接约定](prepared-vm-protocol.md)为准。双架构真实模板的正常上传和恢复路径已由下述 Actions 验证，不能据此推断全部故障路径都完成线上验收。

采用服务端建议的独立额度和统一预留计账，不能为镜像上传挤掉有效原包；额度不足时拒绝写入并继续冷路径。新镜像完成 Actions 验收前保留有效旧版，替换与回收由服务端维护，工作流不发删除请求。首版沿用共享 Bearer，producer 的仓库名只供追踪，不代表权限隔离。

服务端代拉留作后续选项：私有 Actions artifact 网页不是可持久下载地址，短时签名地址也不能直接复用原包持久队列语义。确认受控来源、凭据和有效期之前不启用，不擅自公开镜像。

## 验收与测速

分别记录下载、启动、依赖准备、镜像封装/上传、cor 安装、GUI/代理/TUN 验证和总耗时。先完成一次冷准备及真实入库，再以同架构、同基础镜像、同环境清单和相同验证范围比较原流程与镜像恢复流程；KVM/TCG、排队及服务器链路耗时单列。先跑一组冷/暖对照，有收益后再扩展至少三组比较中位数；不把上传完成或少装几个包当作已提速。

`target/linux-report/focal-vm.json` 记录 cold/warm/cold_template/cold_after_restore_failure、成功或失败、源归档大小，以及归档、传入、环境检查、候选包下载/剩余等待/传输、应用验证和上传尾部耗时；总耗时含下载与上传收尾。`prepared-vm.json` 单列私网阶段与失败码。报告另外保留 `cloud-init analyze show` 和 `systemd-analyze critical-chain`，不支持时记录未取得诊断，不跳过原就绪检查。候选上传与应用测试可并行，应用失败不能用冷重试掩盖。

客户端元数据请求限 20 秒；两次完整下载共用 300 秒传输预算，上传另限 600 秒且不超过租约，服务端 30 分钟上限不等于客户端会等待这么久。独立格式检查和启动验证另计，任何回退及上传尾部等待都须保留耗时，不以并行上传抹掉成本。

必须实际覆盖未命中、摘要错误、服务不可用、并发发布、恢复失败回退和干净的第二次恢复。只有真实恢复及全部原有验证通过，才能声明镜像缓存已接入；在取得对照证据前不承诺具体提速。

接入审查还须核对三条工作流的所有缓存保存与附件路径、最终 Release 成员：均不得包含预装镜像、基础盘、写入层或它们的二次归档。保留小型清单中的大小、摘要和私网回执即可，不能为了测速证据上传磁盘内容。

### 当前 ARM64 瓶颈与优化顺序

2026-11-11，提交 `d033b60` 的 CI `43027364024` 全部 14 项成功；Ubuntu 20.04 ARM64 job 为 15 分 19 秒，`focal-vm.json` 中 VM 步骤为 846.35 秒，暖恢复成功，内核为 `5.4.0-216-generic`，加速方式为 TCG：

| 阶段 | 耗时 |
| --- | --- |
| 私网镜像查询、下载及校验 | 96.09 秒 |
| VM 启动、SSH 与 cloud-init 就绪 | 225.98 秒 |
| 源码注入与环境核对 | 约 124.26 秒 |
| 候选包查询、下载及传入 guest | 41.47 秒 |
| 应用安装及验证 | 353.86 秒 |

源码注入与环境核对按 `prepared-vm.json` 的 `boot/warm_verified` 总耗时减去 `final_guest_boot` 推算，尚未进一步独立计时。日志中查询候选包后不到一秒即确认附件就绪，41.47 秒主要属于获取、校验和传输，不能算作等待编译；原生 `linux-arm64` job 仅 3 分 35 秒。前一轮 ARM64 job 为 18 分 05 秒，但测试选择和 runner 状态不同，不能把两轮差额视为优化收益。

本次已接入独立 Ubuntu Compatibility：归档只含验证脚本、必要元数据、来源提交标记及本架构冻结索引，移除整仓和 Git 历史；候选包获取与私网恢复、启动并行，guest 就绪后才传包。分开记录归档、传入、环境检查和包下载/剩余等待/传输，保留启动分析，来源、收据、环境和网络断言不减少。脚本回归只能验证接线与失败路径，实际收益待新提交 Actions 对照。

TCG 的 vCPU 数与磁盘配置仍须同范围对照，不能假定更多 vCPU 一定更快；QEMU 支持时默认多线程 TCG。当前 runner 没有 KVM，改启动参数无法启用不存在的硬件加速。可用 KVM 的 ARM64 runner 属于另一个执行环境方案，须先确认权限、隔离及成本，再比较完整 job；这些后续方案尚未实施，不能用容器或用户态模拟冒充 5.4 内核验收。
