# 私网缓存客户端与服务端边界

[返回 CI 与缓存](ci.md)。工作流侧维护客户端和缓存身份；服务端 agent 维护服务实现、部署、数据和自己的 AGENTS.md 等文档。贡献者不需要服务器账号或缓存凭据。

## 协作边界

按用户 2026-11-04 的要求，工作流停止 agent 间请求和反馈通道，不修改或上传 `.github/cache-server/README.txt`，不调用 `/v1/readme` 或 `/v1/feedback`，不维护请求跟踪或反馈附件。现有 README.txt 保留为历史内容，不再自动消费。

仅在需要用户介入或转达时，汇报必要的问题、证据和验收条件，不传达常规状态；本侧不操作服务器部署、数据或文档，也不另建端口、消息箱或后台通信。

停止通信不代表 v4/v5 所涉问题已经解决。Windows ARM64 历史缺片及尚无真实恢复证据的类别仍须按实际证据人工验收；工作流继续执行原有缓存能力门禁、引用检查、下载校验和正常编译回退。

## 客户端与服务端的写入约定

工作流侧负责客户端、缓存 key、回退与协议文档；服务实现、部署及数据修复交由服务端 agent。当前仓库中的旧 `Store`/`Handler` 不作为服务器部署来源；服务端 agent 已反馈修复上线。客户端仍检查实时能力，仓库 CI 不代替服务端真实恢复验收。

客户端在发送归档前通过现有 `GET /health` 检查 `schema: 1`、`status: "ready"` 及字符串数组 `capabilities`。服务端完成实现和失败路径验证后才可声明相应能力：

| 能力 | 服务端必须保证 |
| --- | --- |
| `validated-cache-commit-v1` | 暂存预留容量，先校验内容、长度、SHA256 和运行序号，再提交；拒绝或失败上传不能删除现有有效条目。归档使用不可变物理文件名，发布文件后在同一 SQLite 事务提交逻辑映射及物理回收记录，提交成功后才回收不属于保留 key 的物理孤儿；数据库失败或提交前中断时旧映射仍指向原内容，提交后中断时新映射及文件一致可用。 |
| `rust-index-references-v1` | 每个已发布 `rust/<目标>/index` 引用的分片保持可取；上传单片、超时或中断不能先淘汰旧索引的引用。提交新索引时，在同一临界区核验全部非空分片的组、key、id、大小、校验值及文件存在性，原子发布索引及引用关系，再回收不再引用且不属于保留 key 的物理孤儿文件。容量不足时拒绝新上传，不能留下悬空引用。 |
| `complete-cache-retention-v1` | 接受所有缓存类别的完整可复用内容，独立于 GitHub 的 9 GiB 预算；工作流不淘汰私网 key，也不将 GitHub 淘汰结果同步给私网。同 key 可安全更新，物理去重和服务端自行清理不能破坏活动事务及已发布索引引用。容量不足时明确拒绝新写入，保留有效快照；服务端维护策略由其 agent 管理。 |

修复后的响应示例：

```json
{
  "schema": 1,
  "status": "ready",
  "capabilities": ["validated-cache-commit-v1", "rust-index-references-v1", "complete-cache-retention-v1"]
}
```

Rust 分片上传要求三项能力；普通归档要求安全提交和完整保留两项。旧服务缺少字段、返回 404 或声明不全时，客户端跳过相应保存并记录 `server upgrade required`，继续使用已有缓存、GitHub 缓存或正常编译。服务仍须校验每次写入，不能只添加声明字段。保持现有 `/v1/lookup`、`/v1/blob` 及 `rust-shards-v1` 格式兼容；当前客户端按 `SHA256(key)` 得到逻辑 `id`，不可变物理文件名与此逻辑标识分离。

GitHub 命中时客户端仍逐片核对私网 metadata；保存前再次检查精确命中索引，不能只凭源码 key 跳过。生成分片时每个 key 都重新 lookup，缺失则重新归档上传，不直接复用旧记录；实际下载仍核验完整 SHA256。Rust 源码 key 包含 `crates/` 等目录的 SVG，图标变化仅使精确命中失效，保留兼容的依赖前缀。

服务端交接验收须覆盖：上传新片后中断，旧索引全部可恢复；相同分片 key 的缺片可修复；校验失败和过期序号不淘汰其他组；同 key 文件发布后 SQLite 写入或提交失败，旧快照仍能通过原校验。2026-11-03 用户报告的 Windows ARM64 缺片属于既有损坏，声明能力不会恢复已删除的文件，须由服务端 agent 处理并核验。

## 可选的上游代拉下载

服务端已反馈部署同步导入，单次限时 25 秒；CI `41775979641` 曾观测到同版本 JDK 原始归档导入 `ready`，这不代表所有类别都已实际恢复。客户端仍只在 `/health` 同时声明现有安全提交、完整镜像及 `upstream-fetch-v1` 时，尝试受认证的 `POST /v1/import`；不支持、拒绝、超时或应答不匹配时继续上传 runner 已验证的归档。慢下载、大文件及无公开来源的目录快照保留普通上传。不修改或上传 README.txt，需服务端配合的事项仅交用户转达。

请求采用以下结构；`group/key` 是逻辑存储位置，`path` 是现有归档中的根编号，不允许传服务端绝对路径：

```json
{
  "schema": 1,
  "group": "tools/linux-python-x64",
  "key": "v1-example-approved-download",
  "sequence": 1234001,
  "format": "indexed-tar-gzip-v1",
  "files": [
    {
      "path": "0",
      "url": "https://github.com/example/tool/releases/download/v1/tool.tar.gz",
      "size": 123456,
      "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "mode": 420
    }
  ]
}
```

服务端下载每个原文件，核对完整大小和 SHA256 后，作为普通文件按编号封装为与当前 `pack/unpack` 兼容的 gzip tar，并按原有提交和序号规则发布缓存映射。最终 `/v1/lookup` 返回的是外层归档自身的大小、SHA256 和逻辑 id；不能把原始 Python 压缩包直接当作协议归档。

成功应答为同一 `schema/group/key/sequence` 和 `status: "ready"`；异步接受可用 HTTP 202 与 `status: "queued"`。排队只表示已接受，客户端记录“尚未验证”，后续运行仍查 lookup；不能把排队项当作缓存命中，也不能提前替换旧映射。接受队列须持久化、有界、按同一逻辑身份及序号幂等，旧任务不能覆盖新内容，失败保留旧快照。

服务端必须独立校验 HTTPS、官方主机白名单及每次重定向，禁止凭据 URL、任意端口、私网/回环/链路本地目标与 DNS 重绑定；限制文件数、下载字节、总容量、并发和超时。GitHub 资源 API 只访问公开附件、按资产 ID 拉取，不接收 runner 的 GitHub 令牌，也不将私网认证头转发给上游。客户端提供的 SHA256 仍须与来源和长度一并验收；失败或过期请求不能触发清理。

验收至少覆盖真实冷下载、精确 GitHub 命中时补镜像、服务未升级时回退 PUT、重复/过期请求、校验失败、重定向到私网、队列重启，以及通过原有 lookup/blob 成功恢复。编译对象、安装目录和 Docker 构建镜像仍保留原上传方式，直到另有可验证的拉取来源。
