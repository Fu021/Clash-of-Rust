# 桌面与命令行下载

## 跨桌面慢速定位

各平台更新、Geo 和测速的入口、参数、备用代理差异及取证条件统一见[网络链路说明](../network-paths.md)。未发现 Windows 专属限速不等于已经定位慢速；不能通过取消低速保护或关闭 TLS 校验掩盖故障。下载回退与安装恢复边界如下。

## TUN 下的更新直连

内核直连客户端使用 `socks5h://127.0.0.1:<direct_download_port>` 连接受管 mixed 监听器，SOCKS5 请求携带原域名和端口，避免先由系统 DNS 解析，也不经过 mihomo 的 HTTP 请求转发器。共享下载路线的回归实际检查 SOCKS 协商、原域名、HTTP 路径和响应；Linux 安装验证使用同一种传输完成不可达节点下的真实订阅操作。切换传输不等于已定位历史 HTTP 502 的全部触发原因，仍须核对同提交端到端证据。

关闭 HTTP/系统代理只影响应用层代理选择；请求仍可能进入系统 TUN，再次命中已超时的节点。此前订阅、Geo 和客户端更新都把 `reqwest.no_proxy()` 作为最后的“直连”，因此更改规则模式也不一定能恢复更新。仅在没有 TUN 的本机 HTTP 测试中验证回退不足以覆盖这一问题。

当前内核启动时保留独立回环端口，生成固定 `proxy: DIRECT` 的下载监听器。共享下载顺序为内核代理、不同的系统代理、内核直连、系统网络；相同代理去重。内核直连通过 mihomo 自己的 DIRECT 出站发送，不改全局模式、选择、订阅、保护状态或 TUN。设置中的 `direct_download_port` 是内部端口，启动时自动检查冲突并分配，页面无需手动配置。关闭 DNS 覆盖时保留用户自定义上游；开启覆盖时，直连解析明确使用 `#DIRECT` 并关闭直连解析的订阅策略跟随，防止 DNS 又依赖失效代理。Claude 保护的强制 DNS 策略优先，不为更新自动降级保护；自定义/保护上游不可达时仍明确报失败。

安装包进度只有匹配到自身 TCP 源端口、地址及目标的内核连接记录后才显示实际出站。没有控制接口，或本实例报告 `tun.enable=false`，均不能证明系统没有其他用户或第三方 TUN；系统网络路线在缺少证据时不标作 DIRECT。查询失败保留未知，不借用当前选中节点或其他应用的连接记录。

Windows TUN 由 SYSTEM 服务运行内核，服务快照原先移除全部 `listeners`，使受管 DIRECT 入口不存在，启动健康检查在双架构 TUN 场景持续失败。现在只保留 `127.0.0.1` 上 `http` / `socks` / `mixed`、端口不低于 1024 且未启用 UDP 的监听器（最多四个），丢弃 unix、公网和特权端口项；这既恢复下载回退，也不让用户配置创建特权管道。过滤回归与同提交 Windows 双架构 Actions 仍需验证。

代码回归覆盖固定监听器生成、规则/全局/直连模式、代理失败后转入专用入口。Linux 安装验证在隔离网络中启用真实 TUN，先证明失效节点无法下载，再验证订阅添加与更新成功且活动网络状态未变。Geo、更新发现和安装包沿用同一条共享路线。尚未通过当前提交 Actions 或用户设备复验前，不能声称用户现场已经恢复；本机未操作正在使用的 TUN/DNS。

关闭 TUN 仅解除系统路由接管，不改变仍在运行的内核规则；下载若继续访问 mixed 入口，依然可能使用原配置中的失效节点。独立 DIRECT 入口让回退不依赖当前规则/全局模式，也不要求换成默认直连配置。隔离回归分别覆盖 TUN 开启、关闭及系统代理下更新同一订阅；真实用户网络仍需复验。

TUN 或 Android VPN 保持开启时，也使用上述 DIRECT 入口回退；不要求先关闭接管。Android 的 VPN 是承载 TUN 的系统服务，内核出站通过宿主的 `protect(fd)` 绕过自身 VPN，不等于断开 VPN。桌面的内核出站沿用平台的防回环路径。单纯调用 `no_proxy()` 只移除应用层 HTTP/SOCKS 代理，不能替代这些路径。固定监听器语义与直连解析见 [mihomo 入站配置](https://wiki.metacubex.one/config/inbound/listeners/)和[DNS 配置](https://wiki.metacubex.one/config/dns/)。

下载恢复不等同于其他应用恢复联网。一次测速全部失败后，后台通过两个目标复测全部叶子节点，确认后只提示，不自动改变接管，见[警告与取消边界](network-recovery.md#全部节点不可达时的更新与警告)。确认全失联后通知提供可选的“关闭代理”，仅用于用户主动停止当前实例管理的网络接管，不是更新前提，也不保证其他应用或外部 VPN 恢复。启用 Claude 保护时暂停更新、下载和网络设置修改，外观与只读操作按[操作权限](../claude-protection.md#操作权限)保留；这是保护隔离的一部分，不是把保护当成普通下载故障。

手动订阅、Geo 和 `cor update install` 曾在共享后台锁内等待网络；慢网时其他窗口和命令也无法读取状态。下载改在锁外，最终验证与提交由所有者串行处理。手动订阅提交前核对原订阅、文件摘要和保护状态；定时更新还须核对定时开关。失败或过期结果保留现有数据。Geo 和客户端更新也限制同类任务并发，停止内核会取消尚未安装的下载。

GUI/CLI 的订阅更新在开始下载前也核对当前名称和来源；旧版控制请求和显式导入允许指定新来源，两者下载后均检查原配置未被并发修改。新增的控制字段缺省保留旧请求语义，避免把正常换源误判成过期更新。

本机控制连接中断或超时时，订阅、Geo 和客户端更新取消尚未提交的下载并清理暂存；进入安装事务后继续完成或恢复，不能中途丢弃事务。客户端安装交接一旦开始，系统安装程序可能已启动，断开请求不等于撤销安装。慢速下载、取消、重复请求及订阅被编辑后的回归见 [下载任务](../../crates/client-runtime/src/engine/downloads.rs)和[控制连接](../../crates/client-runtime/src/control/transport.rs)；实际网络、安装授权和设备行为须以同提交 CI、安装验证及用户设备结果为准。

macOS 的 `cor update install` 还会等待 DMG 校验和系统授权；此阶段不能持有共享后台锁。助手暂存后须等待所有者复核更新通道、取消状态与 GUI 身份，并收到提交许可且旧进程退出后才替换应用。取消、交接目录消失或未获许可均保留旧应用；普通权限与管理员授权路径遵守相同条件，放弃交接后清理独立暂存目录。

Windows 下载目标从 `0.6.7-fix.9.session-lifecycle` 起支持安装交接闸门：UAC 等待在后台锁外，安装器在执行任何旧程序退出或替换前等待提交标记与来源进程退出。所有者重新核对更新任务、通道、请求连接与 GUI 身份后才停止内核并提交；过期或取消时安装器保留旧文件。闸门只读交接标记，不由管理员进程向调用方路径写回文件。旧安装包不识别闸门参数，继续沿用原串行交接，等待 UAC 时状态请求仍可能等待；不能向它传入新参数后假定安全。源码回归覆盖锁外等待及失效取消，候选安装验收覆盖未提交、提交但父进程未退出、取消与完成安装；真实交互 UAC 和断电不在自动验证范围。

## 终端安装授权与失败恢复

Linux 无窗口的 CLI 更新先通过共享下载门禁准备安装包，再由前台原账户的复制助手调用 sudo，在终端授权；不沿用后台 `pkexec --disable-internal-agent`，也不把用户数据目录交给 root 重建。非交互输入只用非交互 sudo，`--yes` 不代表系统授权。安装前重新核对来源后台 PID、原数据目录、待安装记录和设置摘要，拒绝已取消、被新请求替换或重复提交的交接；等待授权期间不持有后台锁。

只有提交后才停止后台，安装错误或提交阶段的部分停止会尝试恢复原后台与内核状态，同时保留原安装错误；原内核未运行时仅恢复后台。结果持久化后才清理本次暂存目录。新增事务回归覆盖授权拒绝、安装失败、恢复失败、部分停止、过期/重复交接、内容篡改及安装串行；下一轮须启用现有 CI 的 `extended_tests=true` 执行源码回归，不能只依赖常规代理/TUN 结果。实际终端密码、取消、非交互授权、包管理器失败及恢复场景仍需隔离安装验收，本机不操作正在使用的代理/TUN。用法及强杀/断电边界见[Linux 纯命令行安装](../cli/maintenance.md#linux-纯命令行安装)。

## Geo 恢复与启动

Windows 更新 Geo 后若后台反复报告备份路径不存在，安装目录的 `resources` 完整并不能证明用户数据目录中的 `runtime/geo-transaction.json` 与 `.geo-backup-*` 正常，也不能据此确定备份为何缺失。资源发现失败应同时报告实际程序和查找目录，便于排除另一份程序或错误的 `--resources`。

2026-11-06 的追加清单确认用户仍使用 0.6.6，存在含四份数据及清单的 `.geo-backup-M1uQQq`、多份下载暂存和 672 字节事务。必须先核对事务中的 `backup` 是否指向该目录，不能把“存在一个完整备份”当成“事务引用的备份有效”。当前清单约 10 KiB、下载/备份清单约 1 KiB 也不能直接证明损坏：安装包资源会额外保存发布元数据，运行时下载清单较精简。

沿 Windows 调用链发现独立可落实的缺口：TUN 服务原先递归复制用户运行目录，退出时仅排除根目录的 Geo 数据和配置，仍会回写快照中的旧事务、提交标记及备份/下载/恢复目录。这可能在更新完成后复活旧恢复状态，或覆盖后续事务；尚不能认定是用户现场的唯一触发原因。快照入口和缓存回写现均排除上述宿主所有的 Geo 状态，保留真正的 provider 缓存及节点选择；根目录 Geo/配置排除兼容 Windows 大小写。回归用临时目录覆盖快照入口、已完成更新后的旧事务回写、新事务保护和有效缓存恢复，须由本次 Windows 双架构 CI 验证，不以原有 Geo 文件恢复回归替代。

更新失败时仍须严格核验完整备份后回滚；备份缺失不能当作更新成功。桌面启动另有受限恢复入口：只有备份确实缺失、当前四份 Geo 文件全部通过清单的大小和 SHA256 校验，才保留当前整组数据继续启动。原事务和原清单先保存到 `runtime/.geo-recovery-*`，残余备份保持原位，再解除活动事务；Windows 删除活动记录沿用短时文件占用重试。未证实属于旧清单的成功安装时间清空，不能把中断更新记为成功。备份校验错误、权限拒绝、非法恢复路径或当前数据不完整仍拒绝恢复，保留现场。

该入口不覆盖用户订阅或以安装包旧 Geo 数据替换当前文件，不用于更新失败后的即时回滚。支持报告导出的版本先在原用户/数据目录下执行 `cor diagnose --offline --output cor-diagnose.json`，采集边界见[诊断报告](../cli/runtime.md#故障反馈与诊断报告)；保留原事务、备份和恢复目录，结合准确版本、实际程序路径及本次后台日志核对。0.6.6 尚无该导出参数，先只读提供事务、当前清单及所引用备份的清单内容，不启动更新来收集现场。报告不替代原文件，不要仅删除 `geo-transaction.json` 或要求用户反复重装。

`c1762c3` 的 CI `42076490014` 在六种桌面平台各通过 11 项 Geo 回归，使用临时目录中的真实文件操作和本机 HTTP 夹具。覆盖下载校验失败保留旧文件、更新中断整组回滚、提交失败保留事务、已提交更新的清理重试，以及新旧事务格式下的备份缺失、无效当前数据、损坏备份、非法路径和已证实的旧安装时间。这证明文件恢复和受限启动恢复符合断言，不等同于真实应用更新失败后内核重载及网络恢复的端到端验证；Windows 10 实机、真实下载断流、进程强杀和断电均未验收。现场日志不保证记录了全部事务阶段，备份丢失须结合上述文件排查，不能用隔离回归代替原因判断。

## 订阅客户端识别

推荐客户端和“不支持本机场协议”的 SS 提示节点，不能证明内核将 VLESS 转成 SS，也不能直接认定机场故意封禁。混入 V2rayN/NG 标识可能触发非 YAML 响应；当前只声明 Mihomo 兼容客户端，避免对同一路线重复发送相同的 User-Agent。仅含重复占位节点的配置不能替换用户订阅，但真实节点和 provider 必须保留。格式、错误分类和上限统一见[订阅说明](../subscriptions.md#客户端兼容与格式)；回归以本机 HTTP 夹具验证，不使用真实订阅令牌。

格式错误需在路线回退后保留类型，最终提供简短、可操作的顶部通知；HTTP 拒绝不能误标为格式错误。不要把 YAML 解析器原始错误链展示给用户，其中可能带节点凭据。定时通知由共享快照传递并按事件去重，不用视图失效号表达失败，以免清空测速、检测或规则草稿；迟到结果先复核订阅与调度状态。
