# 本地待办与持续跟进

[Agent 入口](../AGENTS.md#本地待办入口) · [文档导航](README.md) · [循环审查](loop-workflow.md)

本文是待办管理、持续跟进和进度汇报的权威说明。管理规则随 Git 同步。实际任务、issue 线索与授权边界只保存在当前工作区根目录的 `todo/` 中，由 Git 忽略。

## 添加与接手

把需求写成 Markdown 文件放进 `todo/pending/`，例如 `070-订阅编辑.md`；可以只写几句话，也可以复制下方[任务模板](#任务模板)。数字前缀按整数值表示默认顺序，用户明确指定的优先级优先。新任务优先复用已完成、删除后空出的前序编号；添加时检查 `pending/`、`doing/`、`blocked/`，避免与现存任务或系列编号冲突。编号由 agent 分配，不会自动循环；现有任务不因复用而批量改名。排序按数字大小，不依赖文件名字典序。`todo/TEMPLATE.md` 可继续使用，不因完成任务删除。

开始、恢复或换 agent 接手时，先检查当前用户指令、仓库状态以及 `todo/doing/`、`todo/blocked/`、`todo/pending/`，读取各任务的补充、证据和下一步。默认先恢复进行中任务，再按编号处理待办；不能仅凭对话摘要重复实施或删除任务。目录不存在时按需创建，不能把缺少本地目录视为已有任务完成。

| 目录 | 含义与处理 |
| --- | --- |
| `pending/` | 尚未开始；接手前重新读文件，确认目标不存在后移入 `doing/`。 |
| `doing/` | 正在实施或等待本任务的验证；末尾记录进度、证据、验证范围、运行编号和下一步。 |
| `blocked/` | 确实依赖外部条件或维护者决策；写清原因、影响、备选方案与恢复条件，满足后移回 `doing/`。 |

多个 agent 不重复接手仍由其他会话处理的任务；按[仓库占用锁](development.md#仓库占用锁)使用仓库。移动或删除前必须重新读取文件，保留用户新增内容和其他 agent 的有效进度，不批量清空目录。

## 持续跟进

只要 `doing/` 或 `pending/` 有当前获准执行、能够推进的工作，就持续推进，不因完成一个阶段、汇报进度或收到用户消息而停下。用户中途提问、反馈或补充要求时，先简要回应并记录必要信息，然后继续当前任务；明确指定优先处理的新任务先做，完成后恢复原任务。仅在用户明确要求暂停/停止，或所有当前获准执行的任务都暂时无法继续时等待；等待时说明具体阻塞与恢复条件。

用户为某项设置的验收或先后顺序是执行边界：例如要求先验收网站再开始其他待办时，网站未获验收就不能转去做其他任务，即使那些任务排在 `pending/`。远期暂缓、未获授权、依赖外部条件或用户决策的任务不视为当前可执行；不为了避免等待而绕过这些条件。已经需要用户回复的问题不靠时间流逝视为同意。

不因完成一个子步骤、提交代码、触发工作流或遇到可独立解决的问题就结束。先按[改动范围](development.md#按改动选择验证)确定必要验证，只跟进本任务适用的 CI、兼容、安装或其他收尾；持续跟进不意味着给每项任务追加客户端发布全套测试。按[Actions 跟进节奏](workflows.md#actions-跟进节奏)低频查询，失败先定位并修复，相关验证排队或运行中不能标为完成。等待期间可推进不依赖结果的本地工作，仍须遵守来源分支固定及提交顺序，不能提前推送破坏正在进行的验收。

需要维护者决策或外部条件时，只阻塞实际依赖该条件的任务，保留其上下文并推进其他可独立完成的工作。如果全部剩余工作都无法推进，清楚说明所缺条件并等待，不伪称完成、不擅自代替用户决定。全部已授权任务完成后正常汇报，无需凭空增加工作。

持续跟进不扩大权限。沿用会话中已有授权，避免对已授权的常规步骤重复确认；公开发布、签名、版本调整、额外工作流等仍遵守[提交与发布约束](../AGENTS.md#actions提交与发布)。用户明确给定的授权、范围及条件记录在相应本地任务中，不能泛化为所有后续任务的授权。

## 汇报当前 todo 进度

用户说“汇报当前 todo 进度”“看看待办进度”“当前任务进度”等时，按以下格式汇报，并继续推进任务。先重新核对本地任务、工作区和已有证据；远端结果按既定低频节奏查询，不把历史成功套到当前提交。

**当前任务**

| 任务 | 进度 | 已完成与验证 | 下一步 |
| --- | --- | --- | --- |
| 当前任务名称 | 约 80% | 简述已完成内容，注明通过、失败、未执行或仅静态检查 | 简述剩余工作及正在等待的验证 |

**后续安排**

| 顺序 | 后续任务与目标 | 依赖或启动条件 |
| --- | --- | --- |
| 1 | 下一项计划执行的任务 | 当前任务的必要验收或外部依赖 |
| 2 | 后续任务 | 已授权的发布或其他收尾条件 |

**需要你决定**

| 事项 | 备选方案与建议 | 影响及当前安排 |
| --- | --- | --- |
| 实际待决策项 | 列出选项、推荐方案及理由 | 说明阻塞什么、其他工作是否继续 |

没有待决策项时直接写“暂无待决策项”，不要制造选择题或重复索取已有授权。有多个正在推进的任务时分别列出，避免把本轮文档整理的完成度当作整个功能批次的完成度。

百分比是当前任务所需工作与验证的粗略估计，需要有完成内容支撑；不是耗时承诺或整个队列的统一百分比。实现和静态检查结束、尚待 CI 时不能写成 100%；CI 通过后仍须计入该任务要求的兼容、内存、安装或发布验收。只有所有约定验收与收尾完成才标为 100%。长日志留在证据文件中，汇报优先给结果、下一步、必要链接和待决策项。

## 完成与交接

实现、审查及任务所需验证全部完成后，删除对应任务文件，保留目录和可复用模板。验证失败、CI 运行中、尚有用户补充或需要决策时保留任务；纯文档遵守[文档提交规则](../AGENTS.md#actions提交与发布)，不得为记录进度单独触发 CI 或打包。

任务末尾应让下一个 agent 能直接接续：说明已完成的修改、当前提交与工作区、可共享证据、通过与未验证的范围、阻塞条件、已有授权及下一步。优先使用公开 CI 网页编号、来源提交和附件名称；本机临时路径、会话 ID 和锁描述符不作为远端接续依据。恢复时重新核实远端状态；临时证据丢失不能补记成功。正式行为与修复结论归项目权威文档，任务文件中的 issue 说明只作线索，当前状态以 GitHub 为准。

同一工作区换聊天可继续读取本地队列。换机器或重新克隆前如需接续，先单独备份 `todo/`，在目标工作区恢复。现场证据先脱敏，只保留复现条件、结果、来源提交及公开验证入口。

## 任务模板

```markdown
# 任务名称

## 需求

想改什么、目前哪里不方便；几句话即可。

## 验收

- [ ] 期望看到的行为和所需验证。

## 注意

可选：优先级、依赖、限制、已获授权及其条件。

## 进度与交接

由 agent 补充已做内容、提交、证据、验证范围、剩余事项及下一步。
```
